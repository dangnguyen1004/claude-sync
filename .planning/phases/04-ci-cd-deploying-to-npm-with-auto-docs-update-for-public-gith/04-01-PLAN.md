  <action>
    Create `scripts/generate-docs.mjs` that regenerates all docs/ files from source code and project state.

    This script should be run as part of the release workflow before publishing. It updates docs to reflect the current state of the codebase without manual intervention.

    **What to regenerate** (based on existing docs/ files):
    - `docs/ARCHITECTURE.md` — regenerate from src/ file structure and inline comments
    - `docs/GETTING-STARTED.md` — update if CLI interface changed (flags, commands)
    - `docs/DEVELOPMENT.md` — update if project structure changed
    - `docs/TESTING.md` — update if test structure changed
    - `docs/CONFIGURATION.md` — update if configuration options changed

    **Implementation approach**:
    - Read existing docs/ files as templates
    - For each doc, extract current state from source (file list from src/, parse JSDoc comments for API docs)
    - Write updated content back to docs/

    **Simple approach for v1**:
    Since docs are already well-maintained manually, the script can:
    1. Run `git diff docs/` to detect which docs changed since last release tag
    2. Print a warning if docs changed but no matching conventional commit touched them
    3. For initial version, just ensure all docs files exist with current content

    **Actually for this phase**, since docs are already in good shape and manually maintained, the "docs regeneration" can be simplified to a no-op that just verifies docs/ is up-to-date:
    ```javascript
    // scripts/generate-docs.mjs
    import fs from 'node:fs/promises';
    import { glob } from 'node:fs.glob';
    const docs = await glob('docs/*.md');
    if (docs.length === 0) {
      console.warn('Warning: No docs found. Run manually to update documentation.');
    } else {
      console.log(`Verified ${docs.length} docs files present.`);
    }
    ```
    Future phases can expand this to auto-generate API reference from JSDoc.

    **Verification**: Script should run without error: `node scripts/generate-docs.mjs`

  <files>.github/workflows/ci.yml</files>
  <action>
    Create `.github/workflows/ci.yml` that tests on every push to open pull requests and merges to main.

    **Trigger:**
    ```yaml
    on:
      push:
        branches: [main]
      pull_request:
        branches: [main]
    ```

    **Jobs:**
    1. **test** job:
       - Uses `actions/checkout@v4`
       - Sets up Node.js 20 (use `actions/setup-node@v4` with `node-version: '20'`)
       - Runs `npm ci`
       - Runs `npm test`
       - Runs `npm run lint-commits` (for PRs only — not on main merges where commits may not follow conventions yet)

    **Strategy:**
    ```yaml
    strategy:
      matrix:
        os: [ubuntu-latest, macos-latest]
    ```
    (macOS because Claude Code runs on macOS and this tool targets macOS users)

    **Concurrency:**
    ```yaml
    concurrency:
      group: ${{ github.workflow }}-${{ github.ref }}
      cancel-in-progress: true
    ```
    Cancel in-progress runs when a new commit is pushed to the same PR.

    **Full ci.yml:**
    ```yaml
    name: CI

    on:
      push:
        branches: [main]
      pull_request:
        branches: [main]

    concurrency:
      group: ${{ github.workflow }}-${{ github.ref }}
      cancel-in-progress: true

    jobs:
      test:
        strategy:
          matrix:
            os: [ubuntu-latest, macos-latest]
        runs-on: ${{ matrix.os }}
        steps:
          - uses: actions/checkout@v4
          - uses: actions/setup-node@v4
            with:
              node-version: '20'
              cache: 'npm'
          - run: npm ci
          - run: npm test
          - if: github.event_name == 'pull_request'
            run: npm run lint-commits
    ```
  </action>

<task type="plan">
  <name>Task 4: Create release workflow (.github/workflows/release.yml)</name>
  <files>.github/workflows/release.yml</files>
  <action>
    Create `.github/workflows/release.yml` that publishes to npm and creates a GitHub Release on merge to main.

    **Trigger:**
    ```yaml
    on:
      push:
        branches: [main]
    ```
    Only runs on main, not on PRs.

    **Permissions:**
    ```yaml
    permissions:
      contents: write
    ```
    Needed for release-please to create commits and for GH release creation.

    **Jobs:**

    **Job 1: release-please**
    ```yaml
    - name: 'Generate changelog and bump version'
      id: release-please
      uses: google-github-actions/release-please-action@v4
      with:
        release-type: node
        package-name: claude-sync
        default-branch: main
    ```
    release-please creates a PR (not direct merge) with version bump + changelog. After that PR merges, the next main push triggers the publish job.

    **Job 2: publish (runs only after release-please PR merges):**
    ```yaml
    publish:
      needs: [release-please]
      if: needs.release-please.outputs.released == 'true'
      runs-on: ubuntu-latest
      steps:
        - uses: actions/checkout@v4

        - uses: actions/setup-node@v4
          with:
            node-version: '20'
            registry-url: 'https://registry.npmjs.org'

        - name: 'Regenerate docs'
          run: npm run docs

        - name: 'Verify docs updated'
          run: git diff --quiet docs/ || (echo "Docs changed — commit with conventional commit message" && exit 1)

        - run: npm ci

        - run: npm test

        - name: 'Build archive for GitHub Release'
          run: |
            node bin/claude-sync.mjs export claude-sync-${{ needs.release-please.outputs.version }}.tar.gz

        - name: 'Publish to npm'
          run: npm publish --access public
          env:
            NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}

        - name: 'Create GitHub Release'
          uses: softprops/action-gh-release@v2
          with:
            files: claude-sync-${{ needs.release-please.outputs.version }}.tar.gz
            generate_release_notes: true
          env:
            GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
    ```

    **Important notes:**
    - release-please creates a PR first, then the PR merge triggers publish. This is the standard release-please workflow.
    - The `version` output from release-please is used to name the archive file and npm package version.
    - NPM_TOKEN must be configured in repo settings (Settings → Secrets → Actions → New repository secret).
    - The archive is built using the local CLI — this ensures the CLI works end-to-end before publishing.
    - The `generate_release_notes: true` uses GitHub's auto-generated release notes based on conventional commits.

    **Alternative: Combined workflow without release-please PR**
    If the user prefers direct version bump on main (no release PR), replace release-please with standard-version in a single job:
    ```yaml
    - name: 'Bump version and generate changelog'
      run: npx standard-version --release-as minor
    ```
    However, the release-please PR workflow is the recommended approach for open source projects.
